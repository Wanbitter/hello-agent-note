# A 组 · 先用眼睛看（不写任何服务端代码）

5 个操作，全程只用 `curl.exe` 打真实网站。做完你就能"看见"报文了。

## 操作 1 · 看一条请求的完整面目

**【做什么】** 发一个最简单的 GET，把过程全部打印出来。

**【命令】**
```powershell
curl.exe -v https://example.com
```

**【你应该看到】**（节选，`>` 是发出去的，`<` 是收回来的）
```
* Connected to example.com (93.184.216.34) port 443      ← 连上了
> GET / HTTP/1.1                                          ← ① 请求行
> Host: example.com                                       ← ② 自动生成
> User-Agent: curl/8.7.1                                  ← ③ 自动生成
> Accept: */*                                             ← ④ 自动生成
>
< HTTP/1.1 200 OK                                         ← ⑤ 状态行
< Content-Type: text/html                                 ← ⑥ 我是 HTML
< Content-Length: 1256                                    ← ⑦ 体有 1256 字节
<
<html>...                                                 ← ⑧ 体
```

**【这一步做了什么】**
- 你在**客户端**发起了一次完整请求，`curl` 把"它替你说的每一句话"都显示出来了。
- 注意 `>` 那几行：**你只写了 `curl.exe -v https://example.com` 这一句**，`Host`、`User-Agent`、`Accept` 全是工具自动加的。
- `>` 和 `<` 之间那个**空行**是分界线：上面是头，下面是体。
- ⚠️ 你看得见明文，是因为你在**自己这端**；出了网卡这段就被 TLS 加密了（对照《指南》概念 9）。

## 操作 2 · 只要头，不要体

**【做什么】** 有些时候你只关心"这资源在不在、多大"，不想要内容。

**【命令】**
```powershell
curl.exe -I https://example.com
```

**【你应该看到】** 只有状态行和头，没有 HTML 体：
```
HTTP/1.1 200 OK
Content-Type: text/html
Content-Length: 1256
```

**【这一步做了什么】**
- `-I` 发的是 **HEAD** 请求——"跟 GET 一模一样，但别把体发给我"。
- 这是 HTTP 方法里最省流量的一种用法：先问大小，再决定要不要下。

## 操作 3 · 自己加一行头

**【做什么】** 手动往请求里塞一个头，看它出现在报文哪个位置。

**【命令】**
```powershell
curl.exe -v -H "Accept-Language: fr" https://example.com
```

**【你应该看到】** 你加的那一行，出现在自动生成的头**中间**：
```
> GET / HTTP/1.1
> Host: example.com
> User-Agent: curl/8.7.1
> Accept: */*
> Accept-Language: fr          ← 就是你加的这行
>
```

**【这一步做了什么】**
- 你第一次**亲手改写了报文**。`-H` 就是"往请求头里塞一行"。
- 头是 `名字: 值` 的格式，冒号后面那个空格**不能省**（省了就是格式错误）。
- 服务器靠这个头决定给你哪种语言版本——头就是客户端向服务器"提要求"的唯一渠道。

## 操作 4 · 看懂状态码

**【做什么】** 故意制造三种结果：成功、找不到、被重定向。

**【命令】**
```powershell
# ① 成功
curl.exe -s -o NUL -w "状态码=%{http_code}`n" https://example.com

# ② 不存在的路径 → 客户端错
curl.exe -s -o NUL -w "状态码=%{http_code}`n" https://example.com/this-does-not-exist

# ③ 明文访问 GitHub → 被要求换到 https
curl.exe -I http://github.com/

# ④ 让 curl 自己跟着跳
curl.exe -sL -o NUL -w "最终状态码=%{http_code}  跳了几次=%{num_redirects}`n" http://github.com/
```

**【你应该看到】**
```
状态码=200
状态码=404
HTTP/1.1 301 Moved Permanently
Location: https://github.com/
最终状态码=200  跳了几次=1
```

**【这一步做了什么】**
- `-o NUL`：体扔掉（Windows 上垃圾桶叫 `NUL`）；`-w`：只打印我关心的统计。
- `200` = 成功；`404` = **错在你**（路径写错了）；`301` = "不在这儿，去那个地址"。
- `-L` 让 curl 自动跟随重定向——**跟随前后是两个独立的请求**，不是一次请求两个响应。
- 记住这个手感：**状态码的第一位数告诉你该去查谁**（4 查自己，5 查服务器）。

## 操作 5 · 连接是复用的

**【做什么】** 一条命令打两个地址，观察底层 TCP 连接被复用。

**【命令】**
```powershell
curl.exe -v https://example.com https://example.com
```

**【你应该看到】** 第二次请求前出现这一行（而不是重新握手）：
```
* Re-using existing connection with host example.com
> GET / HTTP/1.1
```

**【这一步做了什么】**
- 直接推翻"HTTP 是无连接的、处理完就断开"这句老话（《指南》坑表 #1）。
- 两次请求走了**同一条 TCP 连接**，省掉了第二次的三次握手。
- 这就是 keep-alive。**你以后写 SSE 时，那条连接会一直"复"着不关——长连接就是从这里来的。**

# B 组 · 自己起个服务器（看服务端收到什么）

4 个操作。这一组做完，"报文"对你就不再是抽象概念了。

## 操作 6 · 15 行脚本，把收到的请求原样打印

**【做什么】** 写一个只会"照镜子"的服务器：收到什么就打印什么。

**【代码】** 新建 `lab\echo_server.py`
```python
from http.server import BaseHTTPRequestHandler, HTTPServer

class Echo(BaseHTTPRequestHandler):
    protocol_version = "HTTP/1.1"          # 允许连接复用（对照操作 5）

    def _handle(self):
        # ① 体的长度写在 Content-Length 头里；没有这个头就是没有体
        length = int(self.headers.get("Content-Length") or 0)
        body = self.rfile.read(length) if length else b""

        print("=" * 60)
        # ② 请求行：方法 + 路径 + 协议版本，就是 curl -v 里 "> GET / HTTP/1.1" 那一行
        print("请求行 :", self.command, self.path, self.request_version)
        # ③ 所有请求头，按收到的顺序打印
        print("请求头 :")
        for name, value in self.headers.items():
            print(f"    {name}: {value}")
        # ④ 请求体：空的就明确说空
        print("请求体 :", body.decode("utf-8", "replace") if body else "(空)")

        payload = b'{"ok": true, "msg": "wo shou dao le"}'
        self.send_response(200)                                # 状态行
        self.send_header("Content-Type", "application/json")   # 我回的是 JSON
        self.send_header("Content-Length", str(len(payload)))  # 体有多长
        self.end_headers()                                     # ← 这个空行很重要
        self.wfile.write(payload)                              # 体

    do_GET = _handle        # GET 和 POST 都走同一个处理函数
    do_POST = _handle

if __name__ == "__main__":
    HTTPServer(("127.0.0.1", 8000), Echo).serve_forever()
```

**【怎么跑】**
```powershell
cd F:\Python_Project\My-Fast-api\lab
F:\Python_Project\.venv\Scripts\python.exe echo_server.py
```

**【你应该看到】** 服务器**看起来什么都没发生**，光标停在下一行——**这是对的**，它在监听，没有输出是正常的。别以为它死了。

**【这一步做了什么】**
- 你亲手实现了一个 HTTP 服务器的最小骨架：**接收 → 解析 → 响应**。
- `send_response` / `send_header` / `end_headers` / `write` 这四步，**就是构造一个响应报文的顺序**，和操作 1 里 `<` 那几行一一对应。
- `end_headers()` 就是在写那个**空行**。忘了它，客户端会一直等，页面永远转圈。
- ⚠️ 之后你会看到类似 `127.0.0.1 - - [...] "GET / HTTP/1.1" 200 -` 的行，那是 Python 自带的标准日志，不是你的打印，别混。

## 操作 7 · 用 curl 打它，两边对照

**【做什么】** 在**另一个** PowerShell 窗口里发请求，对照两边看到的东西。

**【命令】**（新窗口，别关掉操作 6 那个）
```powershell
curl.exe -v http://127.0.0.1:8000/hello
```

**【你应该看到】**
- **curl 这边**：`> GET /hello HTTP/1.1`、`> Host: 127.0.0.1:8000`、`< HTTP/1.1 200 OK`……
- **服务器那边**：
```
============================================================
请求行 : GET /hello HTTP/1.1
请求头 :
    Host: 127.0.0.1:8000
    User-Agent: curl/8.7.1
    Accept: */*
请求体 : (空)
```

**【这一步做了什么】**
- **同一份东西的两个视角**：curl 显示"我发出去了什么"，服务器显示"我收到了什么"，**两边必须一模一样**。
- 你在 curl 那边看到的 `Host`，在服务器这边变成了 `self.headers` 里的一项——这就是"报文 → 框架 API"的第一步。
- 从今往后，只要接口不对，你的第一反应应该是：**这两边现在分别是什么？**

## 操作 8 · POST 的两种体：JSON vs 表单

**【做什么】** 用两种方式发 POST，只看体的差别。

**【命令】**（服务器保持运行）
```powershell
# ① JSON
curl.exe -v -X POST http://127.0.0.1:8000/echo `
  -H "Content-Type: application/json" `
  -d '{"question": "hi"}'

# ② 表单
curl.exe -v -X POST http://127.0.0.1:8000/echo `
  -H "Content-Type: application/x-www-form-urlencoded" `
  -d "question=hi&page=1"
```

**【你应该看到】** 服务器那边打印出的请求体分别是：
```
请求体 : {"question": "hi"}
请求体 : question=hi&page=1
```
头里分别是：
```
    Content-Type: application/json
    Content-Length: 20
    Content-Type: application/x-www-form-urlencoded
    Content-Length: 18
```

**【这一步做了什么】**
- 两种体的**字节完全不同**，唯一的区别线索就是 `Content-Type`。
- **服务器凭什么知道该怎么解析体？只有 `Content-Type` 这一个依据。** 你可以做个小实验：JSON 的体配上表单的 `Content-Type`，看服务器会解析成什么（会很荒谬）。
- ⚠️ PowerShell 偶尔会吞引号导致 `-d` 报错。真遇到了就换成 `-d '@body.json'`（把 JSON 写进文件再发），这是个很常见的兜底手法。

## 操作 9 · 换 httpx，看代码 ↔ 报文的映射

**【做什么】** 用 Python 发同一个请求，把"我写的代码"和"报文"对应起来。

**【代码】** 新建 `lab\probe.py`
```python
import httpx

r = httpx.post(
    "http://127.0.0.1:8000/echo",              # → 请求行里的 路径
    headers={"Accept-Language": "fr"},          # → 多出来一行 Accept-Language: fr
    json={"question": "hi"},                    # → 自动变成 JSON 体 + Content-Type
    timeout=5,                                  # → 本地请求也要设超时，养成习惯
)

print("状态码 :", r.status_code)                # 200
print("响应头 :", r.headers["content-type"])    # application/json
print("响应体 :", r.text)                       # {"ok": true, ...}
```

**【怎么跑】**
```powershell
F:\Python_Project\.venv\Scripts\python.exe probe.py
```

**【你应该看到】** 服务器那边多了这样一条打印：
```
请求行 : POST /echo HTTP/1.1
请求头 :
    host: 127.0.0.1:8000
    accept-language: fr
    content-type: application/json
    content-length: 18
请求体 : {"question":"hi"}
```

**【这一步做了什么】**
- 现在把三个视角连起来看：

| 你写的 Python | 变成报文里的 | 服务器怎么读到 |
| --- | --- | --- |
| `"http://.../echo"` 的路径部分 | `POST /echo HTTP/1.1` | `self.path` |
| 域名部分 | `Host: 127.0.0.1:8000` | `self.headers["Host"]` |
| `headers={"Accept-Language": "fr"}` | `Accept-Language: fr` | `self.headers["Accept-Language"]` |
| `json={"question": "hi"}` | `Content-Type` + JSON 体 | `self.rfile.read(...)` |

- **你永远只写左边那列，中间那列是库替你拼的，右边那列是服务端读到的。** 这三列就是《指南》第二节那张图的实物版。

## 操作 12 · 加一个路径参数 + 一个查询参数

**【做什么】** 在 `main.py` 里加两个接口，体会"参数从哪来"。

**【代码】** 加到 `main.py` 末尾（`if __name__` 之前）
```python
# 路径参数：值直接长在 URL 路径里
@app.get("/items/{item_id}")
def get_item(item_id: int, q: str | None = None):
    # item_id 出现在路径里 → 从路径取，且按 int 校验
    # q 没出现在路径里 → 从查询串取，?q=xxx
    return {"item_id": item_id, "q": q}
```

**【怎么测】**
```powershell
curl.exe -s http://127.0.0.1:8000/items/42?q=hello
curl.exe -s http://127.0.0.1:8000/items/abc        # 故意给个非数字
```

**【你应该看到】**
```
{"item_id":42,"q":"hello"}
{"detail":[{"type":"int_parsing", ... "msg":"Input should be a valid integer" ...}]}
```

**【这一步做了什么】**
- 一句话规律：**参数名出现在路径里 → 路径参数；没出现 → 查询参数；是个 pydantic 模型 → 请求体。**
- 你只是写了 `item_id: int`，**校验就自动发生了**——`abc` 没进到你的函数里，FastAPI 提前拦下了。
- 报错信息是 JSON，`type` 和 `msg` 告诉你哪里不合法。**这就是"答案在报文里"的意思。**

## 操作 13 · 故意发一个坏请求，看 422

**【做什么】** 对你的 `/ask` 发一个缺字段的请求。

**【命令】**
```powershell
# ① 正常
curl.exe -s -X POST http://127.0.0.1:8000/ask `
  -H "Content-Type: application/json" -d '{"question":"你好"}'

# ② 缺必填字段
curl.exe -s -X POST http://127.0.0.1:8000/ask `
  -H "Content-Type: application/json" -d '{}'
```

**【你应该看到】**
```
① {"你问的是":"你好","回答":"我还没接入API"}
② {"detail":[{"type":"missing","loc":["body","question"],"msg":"Field required"}]}
```

**【这一步做了什么】**
- `422` = 请求格式合法（是 JSON），但**内容不合规**（少了必填项）。`loc` 指向具体位置，`["body","question"]` 意思是"请求体里的 question 字段"。
- **这个错误不是你的函数报的**——你的函数压根没被执行。FastAPI 在进门处就拦住了。
- 记住这条排查链：**400/422 看请求 → 404 看路径 → 500 看自己的代码**。

## 操作 14 · 用 response_model 砍掉多余字段

**【做什么】** 让接口"少返回"一个字段，看 FastAPI 怎么处理。

**【代码】**
```python
class Answer(BaseModel):
    reply: str

@app.get("/leak", response_model=Answer)
def leak():
    # 故意多返回一个 password
    return {"reply": "这里是回答", "password": "不该让你看见"}
```

**【怎么测】**
```powershell
curl.exe -s http://127.0.0.1:8000/leak
```

**【你应该看到】**
```
{"reply":"这里是回答"}
```

**【这一步做了什么】**
- `password` 被**静默丢弃**了。`response_model` 不只是文档，它是**输出的过滤器**。
- 现实意义很大：数据库对象往往有一堆内部字段（密码哈希、软删除标记），**一个 `response_model` 就能防止手滑泄露**。
- 反过来记：**pydantic 对未声明的字段一律丢弃**——收进来时丢、发出去时也丢。这是特性，不是 bug。

## 操作 15 · 用 HTTPException 控制状态码

**【做什么】** 让接口在该失败的时候返回正确的状态码。

**【代码】**
```python
from fastapi import HTTPException

@app.get("/items2/{item_id}")
def get_item2(item_id: int):
    if item_id > 100:
        # 状态码 + 说明，客户端能正确判断"这单没成"
        raise HTTPException(status_code=404, detail="这个 id 不存在")
    return {"item_id": item_id}
```

**【怎么测】**
```powershell
curl.exe -s -o NUL -w "状态码=%{http_code}`n" http://127.0.0.1:8000/items2/5
curl.exe -s -o NUL -w "状态码=%{http_code}`n" http://127.0.0.1:8000/items2/200
```

**【你应该看到】**
```
状态码=200
状态码=404
```

**【这一步做了什么】**
- 对比一下"返回 `{"error": "不存在"}` 并配 200"这种做法：**客户端看到 200 会以为成功**，得解析体才知道失败——所有调用方都得写额外逻辑。
- **错误用异常抛，不用返回值表示。** 这样 `/docs` 里也能标出来，客户端库（`httpx` 的 `raise_for_status()`）也能自动识别。

## 操作 16 · 亲手把服务卡死（本组最重要）

**【做什么】** 用三种写法实现同一个"睡 3 秒"，并排跑两个请求，掐表看差别。

**【代码】**
```python
import time, asyncio

@app.get("/slow-block")            # ① 同步 def
def slow_block():
    time.sleep(3)                  # FastAPI 会把它丢进线程池 → 不卡别人
    return {"who": "同步 def"}

@app.get("/slow-await")            # ② async def + await
async def slow_await():
    await asyncio.sleep(3)         # 让出控制权 → 不卡别人
    return {"who": "async await"}

@app.get("/slow-dead")             # ③ async def + 同步阻塞 ← 灾难
async def slow_dead():
    time.sleep(3)                  # 整个事件循环被你按住 3 秒
    return {"who": "async 里 time.sleep"}
```

**【怎么测】** 新建 `lab\two_at_once.py`
```python
import threading, time, httpx

def hit(url):
    t = time.time()
    httpx.get(url, timeout=30)
    print(f"{url:35s} 用了 {time.time() - t:.1f} 秒")

for path in ["/slow-block", "/slow-await", "/slow-dead"]:
    print(f"--- 同时发两个请求到 {path} ---")
    url = "http://127.0.0.1:8000" + path
    threads = [threading.Thread(target=hit, args=(url,)) for _ in range(2)]
    for t in threads: t.start()
    for t in threads: t.join()
```

**【你应该看到】**
```
--- 同时发两个请求到 /slow-block ---
.../slow-block  用了 3.0 秒
.../slow-block  用了 3.0 秒
--- 同时发两个请求到 /slow-await ---
.../slow-await  用了 3.0 秒
.../slow-await  用了 3.0 秒
--- 同时发两个请求到 /slow-dead ---
.../slow-dead   用了 6.0 秒      ← 变成了 3 + 3，串行了
.../slow-dead   用了 6.0 秒
```

**【这一步做了什么】**
- 前两种**并发**（两个请求一起睡，总共 3 秒），第三种**串行**（一个一个睡，总共 6 秒）。
- 原因：`async def` 表示"这个函数会主动让出控制权"；你在里面写 `time.sleep`，**控制权根本没让出去**，整个服务就陪着你等。
- **这就是为什么 agent 项目里这个坑特别致命**：调 LLM 一等等十秒，如果写错，**整个服务在这十秒里不响应任何人**。
- 正确改法二选一：① 老实用 `def`（FastAPI 自动进线程池）；② 坚持 `async def` 就把阻塞调用换成 `asyncio.to_thread(...)` 或异步库。

## 操作 17 · 最小 SSE：两种写法对比

**【做什么】** 写两个"每秒推一条"的接口，看新老写法的差别。

**【代码】**
```python
import json
from fastapi.responses import StreamingResponse          # 老写法用这个
from fastapi.sse import EventSourceResponse              # 新写法（FastAPI ≥ 0.135）
from collections.abc import AsyncIterable

# 老写法：自己拼 SSE 的文本格式（书上第 14 章就是这么写的）
@app.get("/stream/old")
def stream_old():
    def gen():
        for i in range(3):
            # SSE 的格式：data: 内容，然后一个空行
            yield f"data: {json.dumps({'i': i}, ensure_ascii=False)}\n\n"
            time.sleep(1)
    return StreamingResponse(gen(), media_type="text/event-stream")

# 新写法：直接 yield 对象，格式交给框架
@app.get("/stream/new", response_class=EventSourceResponse)
async def stream_new() -> AsyncIterable[dict]:
    for i in range(3):
        yield {"i": i}              # 转义、data: 前缀、事件分隔，全自动
        await asyncio.sleep(1)
```

**【怎么测】**
```powershell
curl.exe -N http://127.0.0.1:8000/stream/old
curl.exe -N http://127.0.0.1:8000/stream/new
```

**【你应该看到】** 两条命令都是**每秒蹦一行**，而不是等 3 秒一次性出来：
```
data: {"i": 0}

data: {"i": 1}

data: {"i": 2}
```

**【这一步做了什么】**
- `-N` 关掉 curl 的缓冲，否则你会以为"没流式"。**这是排查流式问题的第一个开关。**
- 老写法让你看清 SSE 的本质：**就是一段格式约定好的纯文本**，`data:` 开头、空行结尾。
- 新写法是框架替你拼这段文本。**先写老的（理解），再写新的（实用）**，两个都跑一遍你就真懂了。
- ⚠️ 流式一旦开始，**状态码就改不了了**：中途出错只能发一条 `data: {"type":"error", ...}` 当消息（这就是书上那段 try/except 的原因）。

## 操作 18 · 假 agent + session_id（不花钱）

**【做什么】** 用假回答模拟一个"记得上一句"的 agent，体会无状态 HTTP 怎么缝上有状态的业务。

**【代码】**
```python
SESSIONS: dict[str, list[str]] = {}      # 反面教材：会话表放在内存里

class ChatIn(BaseModel):
    session_id: str                      # 客户端每次都带上来（HTTP 无状态）
    text: str

@app.post("/chat")
def chat(inp: ChatIn):
    history = SESSIONS.setdefault(inp.session_id, [])   # 用 id 捞出上下文
    history.append(inp.text)
    return {
        "reply": f"你说的是「{inp.text}」，这是你第 {len(history)} 次说话。",
        "history_len": len(history),
    }
```

**【怎么测】**（两次用**同一个** `session_id`）
```powershell
curl.exe -s -X POST http://127.0.0.1:8000/chat `
  -H "Content-Type: application/json" -d '{"session_id":"u1","text":"你好"}'
curl.exe -s -X POST http://127.0.0.1:8000/chat `
  -H "Content-Type: application/json" -d '{"session_id":"u1","text":"我叫小明"}'
```

**【你应该看到】**
```
{"reply":"你说的是「你好」，这是你第 1 次说话。","history_len":1}
{"reply":"你说的是「我叫小明」，这是你第 2 次说话。","history_len":2}
```

**【这一步做了什么】**
- 服务器**不认识你**（HTTP 无状态），它只是每次拿 `session_id` 去 `SESSIONS` 里查——**状态是被"带"进来的，不是被"记住"的**。
- 这个 `SESSIONS` 字典能跑通，但它有三个致命问题，正是《指南》阶段三 3.1 那张表在解决的：
  1. **重启就丢**（服务一停，会话全没了）
  2. **多 worker 不共享**（开了 4 个进程，请求落到别的进程就"失忆"）
  3. **永不清理**（跑一个月，内存里躺着几十万条会话）
- 你后面接真 agent 时，就是把 `SESSIONS` 换成 SQLite 或 Redis，再把 `history` 喂给模型——**结构一模一样，只是仓库换了**。
